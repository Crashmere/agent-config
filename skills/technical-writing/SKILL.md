# 技术方案设计与技术文档编写

适用范围：技术方案设计、技术方案文档、项目概览与复盘、技术回复、代码解释、代码注释及维护文档。

## 一、设计前置与权衡原则

1. **优先检查复用与收敛**：新增设计前，先核查现有组件、接口、工作流或数据模型是否已能支持目标需求；当多个设计承担同一职责时，考虑合并方案或抽取公共行为。
2. **控制抽象成本**：在复用与通用性之间权衡实现、理解与维护成本。仅在明确的共性需求成立时引入抽象，并使抽象边界与实际需求相匹配。
3. **写明关键取舍**：在方案中直接说明对最终选型产生实质影响的权衡（tradeoffs）及取舍依据。

## 二、内容组织与详略分配

1. **围绕读者任务与决策组织**：尽早给出结论或核心设计，再展开理解该结论所需的因果关系或数据流。同一段落内保持连贯的抽象层级，并将实现细节与它所解释的设计意图关联起来。
2. **按对理解与决策的影响分配详略**：重点阐述核心逻辑、重要取舍以及影响正确性或使用的约束。常规的解析、格式转换、校验和错误处理仅作概括，除非它们决定业务语义或方案能否成立。凡省略后会导致实质性误解或不同实现的细节，必须保留。
3. **单一主说明处**：每个要点只在一个主要位置完整解释——概览可点明关键决策，后续章节再补充机制、证据或实现细节，必要时简短回指。删除重复的重要性宣称、仅复述本节内容的结尾总结，以及只用于预告下一节的过渡句。
4. **结构形式服从内容**：推理想法用连贯段落，真正并列的条目用列表，对比或映射用表格，在有助于澄清处补充标题、示例、代码片段和图表。按问题规模组织结构，不硬套固定模板，也不把连续推理拆成大量细碎小节。

## 三、叙事、论证与管理层视角文档

编写项目概览、复盘、案例分析、收益分析等叙事性、论证性或面向管理层的文档及段落时，采用“管理层汇报”而非“实现规格说明书”的表达高度：

- **新闻式渐进披露**：开篇即呈现全局图景、核心设计重点与核心价值，随后依次展开背景与痛点、问题评估、整体架构与各模块细节，使读者在开头即可掌握要义，仅在继续深入时接触更细的层次。
- **聚焦论证主线**：围绕具体痛点、方案对比与评估、关键设计洞察、复杂度/收益/扩展性之间的平衡，以及由此带来的技术与业务收益展开论证。
- **系统契约层表达**：在系统、工作流或契约层面解释机制，避免罗列文件路径、函数名、常量等代码级细节。

## 四、事实边界、证据与表达规范

1. **区分现状、拟议与未知**：明确区分现有行为、拟议行为和有重要影响的未知项。事实陈述须锚定代码、配置、接口或可靠来源；性能数据、兼容性承诺和验证结论须有证据支撑。已明确的行为直接陈述，不确定性须精确附着在具体未决事项上。改写已有内容时，完整保留关键事实、数字、主体、归因、适用范围和证据强度，不把不确定写成确定，也不把相关性当成因果性。
2. **以具体机制与证据说明价值**：用“组件在何时做什么、带来什么具体收益或代价”替代关于稳定性、灵活性、性能或重要性的空泛形容，删除不提供信息增量的评价词。
3. **代码注释要求**：注释应解释非显而易见的原因或约束，而不是复述相邻代码；不要在注释中重复函数名。
4. **用词与术语一致**：使用熟悉准确的词汇与明确动词，保留行文顺畅所需的主语、条件和逻辑连接；在保持严肃平实语气的前提下允许短句与自然表达。先删减重复与填充词，再考虑压缩有效解释。全文对同一概念使用唯一一致的术语。

## 五、防冗余与文档修订

1. **直接陈述与检验防御性措辞**：直接说明实际行为、触发条件和后果。对看似防御性的句子，检验其由谁使用、能改变什么理解或决策、删去后什么会变得虚假或产生误导；结合上下文判断其作用，而非机械禁用特定词汇或否定句式。
2. **清除无效对比与赘述**：删去没有具体歧义的人为对比，以及只用于自证勤勉、致歉、预设假想质疑或说明读者无需关心的排除项的句子。将叠加的模糊限定词合并为与证据强度匹配的一个限定词。将用户要求或会改变语义的限制条件紧邻其所限定的论断放置；仅编者可见的核验备注放入工作笔记，不要把无用免责声明塞进脚注。
3. **修订文档时重构为当前视图**：将受影响段落重写为对当前设计、现状与约束的连贯说明。删除已被推翻的结论、废弃分支以及依赖对话上下文的备注（如“此前讨论过……”“本文略去……”）。保留面向新读者的简明选型原因；仅在专用于留存历史的记录中保留历史决策。
4. **完稿整体复核**：交付前通读完整产物（包括图注、导语和交付说明），确认核心语义未被破坏，且已删去的防御性表述未在周边文本重新出现。若原文已足够直接、忠实且无实质改进空间，则保持原样。
