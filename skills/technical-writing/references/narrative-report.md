# 叙述汇报模式编写指南

面向管理层汇报、项目概览、专项复盘、案例分析、收益分析与晋升/阶段答辩。核心目标是在有限篇幅内让读者看清**为什么做、难在哪、怎么破局、拿到什么量化结果**。

## 视角与语气

- **系统与契约层叙事**：站在问题、架构、工作流和业务/工程收益层面解释机制，**不罗列文件路径、函数名、常量名等代码级细节**。详细技术方案、数据看板、排查文档通过引用链接挂在对应位置即可。
- **书面紧凑、去口语化**：禁止“大家好，”“接下来我讲一下……”等口语开场或串场词；文档是供阅读与作为讲解底稿的结构化材料，不是逐字演讲稿。
- **坦诚客观**：如实交代阶段边界、架构取舍代价，以及仍未解决的问题或负向观测指标（如某实验组核心指标出现负向后暂缓扩量），用事实和决策闭环体现专业度。

## 推荐叙事主线（渐进披露）

1. **业务背景与演进主线**
   - 开篇用简洁陈述 + 关键水位指标立住“为什么要做”（例如核心风险指标已压到什么水位、当前重心如何从“控风险”转向“降误伤/提效率”）。
   - 如有多个连续阶段，用表格「阶段 | 核心目的 | 关键动作 | 当前进度」一次性交代全局脉络。
2. **痛点梳理（结构化归因）**
   - 避免大段散文倒苦水，优先用「痛点维度 | 现状 | 具体痛点（影响）」表结构化拆解。
   - 每条现状都要落到具体工程或业务后果（如“修改需走完整发版”“隐式依赖导致静默跳过”“人工对齐费时易错”）。
3. **目标与方案边界**
   - 用双栏表对比**长期目标 vs 本次改造（阶段目标）**，说明为什么不一步到位、本次沉淀什么基础能力、预期把哪些环节的耗时或风险降到什么程度。
4. **核心设计与难点破局**
   - **说明关键取舍依据**：例如为什么选 JSON 配置而不是脚本平台、为什么改造成“先全部识别 → 再统一决策 → 一次性落库”的流水线，重点讲机制优势与演进空间。
   - **难点/痛点对照表**：对于多问题并行的专项或阶段汇报，高频使用两栏表「难点/痛点 | 解决方式」或三栏表「子项目 | 核心做法 | 收益」，必要时在单元格内嵌入精简架构图、对比流程图或监控趋势图。
   - **架构对比**：使用「改造前架构 vs 改造后架构」双栏对比，直观呈现从“强耦合/烟囱式”到“分层解耦/底座复用”的变化。
5. **可靠性验证与协同落地**
   - 重点项目专门交代灰度与验证手段（如本地/PPE 单点验证 → 线上双跑只读 Diff → 分步切流），以及跨角色协同动作（如提醒 PM 口径变化、推动上游或外部服务改进）。
6. **量化收益与后续规划**
   - 使用高亮块（`<callout>`）或分「业务侧收益 / 技术侧收益 / 协作方面」条目收口成果。
   - **必须给机制 + 硬数据对比**：所有“提速、降本、稳定、解耦”的结论都必须附带改造前后对比数据（例如：交付周期从 `0.5～1 天` 降至 `2～15 分钟`、某类需求 `80%` 免发版、失败率从 `20%～30%` 降至 `5%` 以下、无效放出量 `-57.7%`、接入复用涉及 `11` 个下游零改动），并写明通过什么机制达成。
   - 结尾简明列出后续规划（稳定运行观察、待推进优化或暂缓事项的触发条件）。

## 版面与证据组织

- **高密度表格承载复杂对比**：痛点拆解、难点与解法、多子项目成果、线上问题排查（问题现象 → 排查与定位 → 解决与收益 → 下一步）均适合用表格紧凑呈现。
- **图表服务于论点**：监控折线图、命中率/成本柱状图直接放在对应的排查过程或方案选型依据旁，用数据支撑TTL、资源选型或故障前后对比，不单独堆砌无解释的截图。
- **外链分层扩展**：正文只保留关键数字与决策逻辑，细节归因、SQL 测算表、完整技术方案以引用卡片挂在对应小节下，兼顾高管速览与研发深挖。
