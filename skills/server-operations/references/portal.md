# Portal and Resource Declaration Maintenance

ServerPortal (Crashmere/ServerPortal, workspace ~/ali/ServerPortal) provides the application portal, device authentication, read-only resources, restricted cleanup, and manual backups. Its migration target is NAS at /opt/serverportal, loopback port 18085, and /portal/, with Web and local Unix-socket collector together. NAS LAN HTTPS 443, ALI HTTPS 443, and VPS HTTPS 8443 reach that same instance. [Current-state](current-state.md) records activation; [NAS migration](nas-migration.md) owns shared traffic and recovery. AICalendar's `/aicalendar/ingest/v1/` retains its independent Bearer credential; full conversation/original-chunk tables are now part of complete recovery, not an excluded archive type.

<a id="所有权与注册目录"></a>
## Ownership and registry directory

- Each application maintains its name, icon, repository, entry point, port, user, units, databases, backup types, directory purposes, and main APIs only in its own deploy/portal.json. The production file is /opt/<app>/config/portal.json, managed by root.
- Portal display names in name must use English brand names (for example, Yuyan), without appending Chinese names; new services follow this from initial integration. Keep Chinese resource-purpose names and description in declarations; the portal application list does not display description.
- The portal uses registryDir=/opt/serverportal/registry.d, with each <app>.json a root-managed link to /opt/<app>/config/portal.json. The first declaration release creates the link; no central array of registry paths needs maintenance. The old registry array exists only for migration compatibility and cannot be configured together with registryDir.
- The portal checks for declaration changes on requests, caching ordinary requests for at most 2 seconds; /registry activation checks force a reread. It replaces the in-memory snapshot only when the entire declaration set is valid, also invalidating the overview cache and unexecuted cleanup previews. On error, it keeps the last valid configuration running and displays a notice; restarting still requires valid declarations on disk.
- Automatic discovery is limited to the registry directory. Application files, database tables, and runtime status are read from the live system; directory purposes, API descriptions, service ownership, and browsing/cleanup boundaries must be explicitly maintained, not guessed by scanning.

Check API entries against the project's actual routes and API documentation; successful synchronization does not prove content correctness. For the full verification method, see [Portal API list does not match the service](common-issues.md#portal-api-list-does-not-match-the-service).

Each business location and program limits upload and large-document request sizes. Body-size checks are disabled only for the shared internal authentication subrequest, which does not forward request bodies, avoiding 500 errors caused by inheriting the default 1 MiB limit. For the cause, affected scope, and validation, see [Shared authentication rejects large requests](common-issues.md#shared-authentication-rejects-large-requests).

## Shared validation and release protocol

The sole maintained validation source is scripts/validate-portal.py (Python 3 standard library). The maintenance computer runs it from a trusted agent-config checkout; the server uses the same rules through /opt/server-context/scripts/validate-portal.py. When updating the contract, synchronize this script, the ServerPortal integration, and local shared tools, and validate existing declarations. The server needs neither Go/Node nor additional Python packages.

Each application retains a separate deployment identity and minimal sudo scope, with the current maintenance computer's public key in authorized_keys. The root-managed deploy-ssh.sh / deploy-release.sh support two declaration commands:

- portal-check <source-commit> <declaration-sha256>: accepts at most 1 MiB of JSON on stdin, validates declaration ownership, conflicts across the registry, and SHA-256 without writing files; run before replacing the business program.
- portal <source-commit> <declaration-sha256>: performs the same validation, acquires this application's deployment lock and the registry lock, atomically installs the declaration and creates a controlled link, forces portal reload, and verifies the actual SHA-256. Restores the previous declaration/link on failure; records config/portal-source.json on success.

Both commands invoke ServerPortal through the application's existing fixed root release script, which fixes the application name. They cannot upload validators or release scripts, or specify other applications, directories, or arbitrary commands. Declarations fix their own root, runtime user, and URL prefix; units must belong to the application, resources must stay within its directories, configuration/secrets cannot become web-readable, and cleanup is limited to its own backups/releases.

Local releases place portal.json and the program from the same commit in the same local version directory, run a preflight check, then synchronize the declaration after successful program deployment. Declaration synchronization failure causes the local command to fail; a successfully deployed program is not automatically rolled back. First inspect the source marker and portal receipt, then correct the declaration. Program health checks use server loopback; public HTTPS without credentials should return 401.

To update only portal metadata, commit and push the source, then run `make portal` in the project. This command preflights and synchronizes the declaration and verifies the receipt without building or restarting the business program. Declaration provenance is in portal-source.json; program provenance is in current-commit.

<a id="新服务与日常维护"></a>
## New services and routine maintenance

1. Prepare the service, restricted deployment identity, documentation, and Nginx location under the shared rebuild rules. Inherit public authentication and, by default, complete the icons, exact public-access rules, and automated checks required by the [Website icon conventions](conventions.md#website-icons-and-home-screen-shortcuts). The current automatic integration contract is /opt/<id>, a runtime user with the same name, a single SQLite database, and a native backup interface. Implement an explicit adapter first for different storage/deployment models.
2. Add deploy/portal.json and AGENTS synchronization rules to the project, integrate shared validation and the above release protocol into local releases, and update the shared application inventory. The first declaration release automatically registers the service.
3. When data roots, APIs, units, ports, access paths, or backup contracts change, maintain the declaration and corresponding docs in the same commit. Adding or removing ordinary files, photos, backup files, or database records does not require declaration changes. Rebuildable derived data may remain `kind: "cache"` for resource browsing/usage; it must be a data subdirectory containing no database. NAS full backups include stored caches/derivatives rather than deriving copy coverage from that display label.
4. After deployment, verify the portal loading receipt, directory purposes, read-only data tables, and unknown-directory notices. Backup contract changes require corresponding isolated example validation; schedule real restoration drills according to the user, and do not automatically resume deferred tasks.
5. Continue synchronizing documentation with sync-docs.sh; local program releases do not publish docs. Follow the SKILL authorization table for shared architecture and real-data handling when adding/renaming/retiring services.

## Security and backups

The server generates `__Host-portal_device` credentials using Secure/HttpOnly/SameSite=Strict cookies. Server-side grants do not expire automatically; valid accesses renew browser cookies to 400 days, subject to browser limits. Startup migrates still-valid older grants without reviving expired/revoked credentials. Portal renews directly; business locations forward renewal headers through shared Nginx. See [Cookie renewal](common-issues.md#cookie-renewal-with-shared-authentication) for inheritance rules. Resource browsing is read-only and cleanup requires preview/confirmation; root collector access stays on a local Unix socket, with no arbitrary paths, SQL, or remote-root interface.

NAS configuration uses the explicit `origins` array; legacy `origin` is used only when the list is empty. A browser write must both match the allowed HTTPS set and equal the request's HTTPS Host/port. Preserve `$http_host` upstream so VPS `:8443` is not lost. Each server IP needs its own first login; port differences are Origin boundaries but not cookie isolation. LAN access has the same authentication contract.

### Public NAS Device Setup

Portal's `/portal/connect` page and its exact `/info`, `/ca.crt`, `/apple.mobileconfig`, and `/qr.png` children accept anonymous GET/HEAD requests. These routes provide installation instructions, public root-certificate metadata, a DER root download, a root-only Apple profile, and a QR code for the configured VPS setup URL. They do not authorize a device or expose business resources; all other Portal APIs and business authentication remain unchanged.

NAS configures `onboarding: {caCertificate, lanOrigin, publicOrigin}` using `/etc/nas-ca/ca.crt`, its exact LAN HTTPS Origin, and the primary VPS HTTPS Origin including `:8443`. Both Origins must belong to `origins`. The root collector reads and validates only the configured public root and existing leaf, checks their chain and LAN identity, and re-encodes the certificate rather than returning raw file contents. Private keys and the root-only directory permissions remain unchanged. Downloads and QR targets cannot be selected through request paths, query parameters, or Host headers. Omitting `onboarding` disables the materials; invalid certificate/setup state reports unavailable without disabling business authentication.

New devices use VPS's already trusted HTTPS to obtain the materials before connecting directly to NAS. The page offers iPhone/iPad, macOS, Windows, and Android instructions with a manually adjustable platform suggestion. Installation and OS trust confirmations remain user-operated; iOS/iPadOS require a separate full-trust confirmation, and some Android applications do not accept user-installed CAs. The page neither probes the OS trust store nor automatically switches entrances. Actual NAS browser/client trust and the separate initial NAS login remain device acceptance work. ServerPortal `docs/OPERATIONS.md` owns the platform steps and endpoint details.

The NAS source template is ServerPortal `deploy/portal.nas.example.json`. It requires `manualBackup: {mount, uuid}`, with `exports` strictly below the mount, and configures `certificateTimer`/`certificateService` for `nas-lan-tls`. The `/etc/server-maintenance-host=nas` marker rejects omission of the manual-backup contract. The actual external UUID is not yet known: empty UUID or absent/wrong volume reports backup unavailable, while Portal startup/authentication/resource browsing still work. Never substitute an internal exports directory.

New NAS jobs use `scope=full`, standalone unencrypted `.tar.gz` recovery sets; compression is required, without a new key workflow or incremental chain. Old encrypted/incremental packages retain their existing restore requirements. Cold-copy coverage includes full databases/WAL/upload state and stored derivatives plus programs, configuration, declarations, identities, Portal grants/registry and registered private NAS material, including `/etc/nas-ca`, `/etc/nas-tunnels`, and unresolved `/var/lib/server-upgrades` protection. Routine backup/release history is not recursively copied. Gateway live state remains an agent-captured separate package, including the active VPS proxy private configuration.

The shared full-job sequence and locks are in [NAS migration](nas-migration.md#manual-full-backups): verified external volume, exclusive global maintenance lock, drain/pause, complete external staging, resume prior active units, compress immutable staging, read-back/flush, then remove only successful job staging. Portal captures its devices through the coordinated state lock. `/run/lock/serverportal-backup-paused.json` is a volatile interrupted-job receipt for resuming paused services, not a data backup. Failed jobs do not publish completion or fall back internally.

Routine backup jobs and rotation are not scheduled on NAS. Upgrade-only local protection is root-private and uses [the shared release lifecycle](release.md), not ordinary Portal cleanup. Agent SSH performs restoration into an isolated path before approved production replacement; Portal does not add a web production-restore flow. ServerPortal docs/RESTORE.md and docs/VERIFICATION.md own package format, actual recovery acceptance, and rebuild order. A real external-drive recovery drill remains pending the actual volume.
