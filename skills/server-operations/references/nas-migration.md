# NAS Applications and Public Gateways

This reference owns the shared application placement, gateway, manual backup, and recovery contract for `nas`, `ali`, and `vps`. [Current-state](current-state.md) records actual activation and outstanding acceptance. Yuyan document 832 under document 375 contains the user's complete Chinese migration plan. Public repositories contain templates and SSH aliases, not private addresses, credentials, or recovery packages.

## Host Roles and Traffic

In the target topology, `nas` runs the only active instances of Ledger, FeeTable, FabricWorld, RecipeBox, Yuyan, ServerPortal, AICalendar, and Aura and owns their authoritative data. Paths, application users, and loopback ports 18080-18087 remain unchanged. Portal Web and its local Unix-socket collector stay together on `nas`; Ledger-to-FabricWorld calls remain local. There are no duplicated lightweight databases or automatic failover to old ALI data.

| Entrance | TLS and routing | Upstream |
| --- | --- | --- |
| `nas` LAN IPv4, HTTPS 443 | Local-CA certificate, Portal authentication, application-owned Nginx locations | NAS loopback application ports |
| `ali` public IPv4, HTTPS 443 | Existing trusted IP certificate, Portal authentication, same application locations | Individual loopback reverse-SSH listeners to NAS |
| `vps` public IPv4, HTTPS 8443 | Its own trusted IP certificate, Portal authentication, same application locations | Individual loopback reverse-SSH listeners to NAS |
| `vps` TCP 443 | Existing sing-box REALITY/Vision proxy | Independent proxy traffic; not an HTTP application gateway |

NAS initiates supervised OpenSSH reverse forwarding to both gateways. Dedicated restricted identities, separate managed connections, strict gateway host-key verification, loopback-only remote listeners, keepalives, reconnect, and forwarding-bind failure detection are required. Forward application ports rather than adding another HTTP rewriting hop. Gateway maintenance access to NAS uses a separately restricted loopback management forward; it does not expose NAS SSH publicly. Deployment still targets NAS, independently of the selected public URL.

Sources are `assets/nas/reverse-tunnel@.service`, `assets/nas/tunnel.conf.template`, and `assets/gateway/30-nas-tunnel.conf`. NAS runtime identity `nas-tunnel` reads root-managed `/etc/nas-tunnels/{ali,vps}.conf`, corresponding `.key` files, and `known_hosts`. Gateways allow that identity only the listed remote listeners, no local forwarding/shell/PTY/agent. Ports 18080-18087 map to the same NAS ports; gateway loopback 22022 maps to NAS SSH 22. Each gateway's own loopback HTTP 80 includes the application locations, so inspection uses those application forwards without another HTTP-tunnel port. An optional maintenance-computer NAS-via-VPS alias can use 22022 while preserving the local NAS alias.

On each gateway, the dedicated identity's `.ssh` directory is root-owned with group `nas-tunnel` and mode 0750; `authorized_keys` uses the same ownership and mode 0640. OpenSSH must be able to read it as the authenticating user while that user cannot edit the key restrictions. A root-only 0700 directory blocks that read. Validate the effective Match configuration and a fresh restricted connection after changes.

The maintained gateway drop-in applies `ClientAliveInterval 15` and `ClientAliveCountMax 3` only to `nas-tunnel`, complementing NAS's client-side keepalives. VPS runs this server-side policy; ALI's live drop-in remains unchanged and has not received this rollout. A fresh tunnel connection is required after an sshd reload because existing sessions retain their settings. See [stale reverse-SSH recovery](common-issues.md#stale-reverse-ssh-session-blocks-tunnel-recovery).

Both public gateways reach the same NAS data. After cutover, ALI retains its original application programs, configuration, data, and history frozen with retired units disabled as the last migration-point fallback. These retired application materials receive no further upgrades, backup additions, documentation maintenance, or cleanup. ALI's current forwarding and certificate renewal remain active infrastructure. Continuing that forwarding preserves the old public address and cookies; it does not keep an old writable application instance. Ending forwarding or canceling ALI is separate from this migration.

Family devices use the NAS address directly for large imports and media transfers. Relative application/media URLs keep LAN traffic local. Public throughput is bounded by the home uplink and gateway route/provider limits. NAS remains locally usable if either public gateway or the Internet is unavailable. The existing proxy and its client imports are preserved; Hiddify's LAN bypass rules must keep private NAS traffic direct.

## HTTPS and Authentication

`ali` and `vps` each obtain a public certificate for their own IPv4. An ALI certificate cannot cover a different VPS address. HTTP-01 uses gateway port 80; a certificate issued there can serve VPS HTTPS on 8443 without taking the proxy's 443 listener. Public IP certificates have roughly 160-hour validity and require automated renewal. Certificate/security/time-maintenance timers continue under the manual backup policy.

NAS uses `/etc/nas-ca` for private CA and leaf-certificate materials. The leaf SAN includes the selected LAN IPv4. Devices import and trust only the CA root; the private signing key remains server-side and must be included when capturing recovery materials for that CA. Leaf renewal under the same CA does not require importing another root. Use normal OS trust, including iOS full trust where required, and validate both the browser and Aura client; do not bypass certificate checks. [HTTPS](https.md) owns signing/renewal details.

New devices can open Portal's anonymous `/portal/connect` page through trusted VPS HTTPS, obtain the public root or Apple profile, and follow the selected iPhone/iPad, macOS, Windows, or Android instructions before opening NAS directly. [Portal maintenance](portal.md#public-nas-device-setup) owns this narrow public bootstrap. OS trust confirmations and the initial NAS login remain user-operated.

The user deferred a router reservation, wired-network migration, and further stability investigation. The present DHCP address remains the migration input, not a guaranteed fixed address. If DHCP changes it, update trusted connection settings, NAS leaf SAN, configured Origins, Portal's `onboarding.lanOrigin`, and LAN shortcuts together. The unresolved freeze history and unverified automatic startup after complete power loss remain operational risks, not blockers that have silently been declared solved.

Business pages and APIs at all user-facing entrances retain Portal authentication and exact HTTPS Origin checks. Include NAS, ALI, and VPS with `:8443` in the configured set. Preserve `__Host-portal_device`, Secure/HttpOnly/SameSite behavior, grants, renewal, and revocation. The three server IPs require separate initial logins because cookies are host-bound; Origin checks also include the port, although cookies themselves are not isolated by port. Nginx overwrites the forwarded protocol and preserves the full request Host, including port, with `$http_host`. Bearer-authenticated AICalendar ingest remains independent. Unauthenticated business inspection stays loopback-only and SSH-authorized; the public device-setup page is not a business-inspection interface.

## Manual Full Backups

The agent exclusively owns backup, verification and recovery. Portal has no backup/recovery page, API, archive download, job worker, CLI or external-volume configuration. The standalone tool and complete operating procedure are maintained in [Agent backup and recovery](backup-recovery.md). NAS uses a manually attached external filesystem configured independently at `/etc/server-recovery.json`; insertion never triggers a backup and missing media never redirects writes internally.

Every routine recovery set is one standalone full compressed NAS/VPS package, without a new encryption-key workflow. NAS coverage includes all database tables, conversations/chunks, originals, incomplete uploads, derivatives, programs/private configuration, identities/ownership, Portal grants/registry, local CA and tunnels. VPS gateway/proxy material is received uncompressed on NAS and included in the same package, with separate host namespaces and capture times. Ordinary backup/release history is excluded; unresolved upgrade protection is included. Frozen ALI receives no maintenance. [Agent backup and recovery](backup-recovery.md) owns the short request phrases, permissions and execution details.

Cold capture pauses required active NAS writers, including Portal Web/collector and registered background units, under the exclusive maintenance lock. Only previously running units resume, before compression. Both hosts' immutable state and the single compressed package temporarily occupy root-private NAS staging; external readiness and capacity are prerequisites, not an internal fallback. Copying, complete external read-back and flush precede successful task-staging deletion. Failure retains useful NAS/external staging and interrupted unit receipts for agent investigation. Agents report long-phase progress, speed and ETA at least every 30 seconds. Packages/evidence remain agent-owned, not Portal state.

The user waives a retained local migration recovery point. Task-created Mac seed archives and temporary private packages are relay and acceptance materials, not a final retained Mac archive; delete them after all automatable migration acceptance succeeds. The frozen ALI installation remains the last migration-point fallback and excludes subsequent NAS writes. Using it later requires a confirmed recovery point and acceptance of any resulting data loss.

Pre-existing maintenance-Mac backups and pre-LVM NAS recovery material remain protected unless explicitly identified as redundant with evidence; frozen ALI materials remain untouched. Manual recovery points mean writes after the last successful complete backup can be lost.

## Upgrade and Recovery Boundaries

Upgrade-only local protection uses the explicit NAS marker `/etc/server-maintenance-host`, root-private `/var/lib/server-upgrades`, and the shared maintenance/deployment locks. It preserves complete data while runtime and affected-data checks run. Success deletes that upgrade's protection immediately; failure, incomplete verification, or cleanup errors retain identified protection. [Retention](retention.md) and [Local releases](release.md) own this lifecycle. Legacy daily application backup/retention tasks and ALI HBR clients are stopped during cutover without deleting historical materials.

FabricWorld and RecipeBox retain their native expired-record/media/upload cleanup through separate NAS-only `*-cleanup.service`/`.timer` units, without invoking backup or backup pruning. Each runs as its runtime user under a shared maintenance lock and an exclusive application deployment lock. Install `assets/nas/server-maintenance.tmpfiles.conf` at `/etc/tmpfiles.d/server-maintenance.conf` and create its root-owned 0644 lock files before enabling these timers. Read-only descriptors let runtime cleanup acquire locks without changing them; root deployment and backup use the same inodes. Application declarations include these units so a cold backup pauses them as writers.

An agent performs recovery through trusted SSH. Verify and extract into an isolated path, inspect databases, complete media/archive coverage, versions, permissions, and credentials, then confirm the recovery point before production replacement. Do not start restored Yuyan cleanup before inspecting older history/media that would expire. After Aura recovery, reconcile Origin-keyed upload receipts so missing server originals are not treated as already uploaded.

Restore NAS applications on compatible Ubuntu amd64; rebuild VPS gateway/proxy on AlmaLinux with that platform's package, firewall, and certificate mechanisms. Do not copy Ubuntu APT/snap/UFW assumptions or Alibaba agents to VPS. A new gateway IP requires a matching certificate and client settings. Preserve both local administrative access and a restricted remote maintenance route; an application tunnel being down must not be treated as permission to expose internal services.

## Cutover and Acceptance

Stage source, artifacts, identities, certificates, gateways, and tunnel configuration while ALI production stays authoritative. Any preliminary data copy is staging, not the final recovery point. During the authorized cutover, pause clients and writes, drain operations, stop old applications/background jobs, capture complete consistent state, verify the final complete transfer from the frozen ALI source, then activate those exact NAS copies. Stop the old Portal Web/collector and disable retired ALI application/backup/retention/HBR units before reassigning their original ports to forwarding.

Validate direct NAS state, all three authenticated entrances, trusted TLS, path/header/streaming behavior, uploads/downloads, Ledger integration, AICalendar Bearer ingest, and proxy 443 continuity. Record the absent external-volume prerequisite and device trust/login results rather than treating CLI TLS checks as actual-device acceptance. The user performs physical CA trust, initial NAS/VPS device logins, and external-drive insertion; the agent handles configuration and all automatable checks. Sync owning source configuration, declarations, active project docs, and shared copies to the hosts whose role actually changed, without updating frozen ALI application materials.

After all automatable migration acceptance succeeds, remove task-created Mac relay materials and confirmed redundant NAS/VPS staging, obsolete backups, and outdated files. Preserve current runtime/configuration/keys, the frozen ALI installation, protected pre-existing backups, and unresolved failed-upgrade protection. Device trust/logins and real external-drive acceptance remain separately recorded until actually completed.

If NAS has accepted no new writes, failure can return to the frozen ALI source after stopping conflicting NAS listeners. Once NAS has accepted new writes, it is the latest source: repair gateways or use a compatible program rollback; reverting to old ALI databases would lose data. Any host/data rollback then requires a fresh consistent transfer or separately confirmed recovery point. Do not enable automatic stale-data failover.
