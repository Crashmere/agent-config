## Media processing policy

All media processing on `nas` must use the GPU wherever practical. Prefer the RTX 3070 for supported image and video decoding, encoding, resizing, rotation, filtering, preview generation, and other compute-heavy media operations. Apply this default when adding or maintaining any NAS application or media workflow. Choose GPU-capable libraries and verify actual GPU execution under the application's runtime identity; the presence of a GPU or an encoder name alone is not evidence that a job used it.

Keep original bytes, color interpretation, orientation, grouping semantics and output quality correct. Use CPU work for unsupported formats/operations, metadata and I/O, and compatibility-sensitive steps whose GPU result has not been shown equivalent. Report the actual engine and fallback reason where processing progress is exposed. Reuse GPU contexts for batches, bound memory/concurrency on the shared 8 GiB device, and release idle contexts so runtime power management can suspend the GPU. Measure representative end-to-end work before making speedup claims.

Aura uses GPU image resizing/JPEG encoding and video CUDA/NVENC, with CPU standard-pixel hashing and color/codec fallbacks. Curio reuses the same image environment for still derivatives and NAS's FFmpeg CUDA/NVENC for video, with its own workers and codec/CPU fallbacks. FabricWorld and RecipeBox currently use libvips CPU image pipelines; Yuyan has its own image-variant pipeline. Apply this policy when maintaining those applications as well. Each project owns its implementation and its actual accelerated stages; the existing CPU pipelines remain unchanged.

### NVIDIA driver maintenance

The GPU uses distribution-signed modules for the running `7.0.0-38-generic` kernel and matching 595 server userspace packages. Check `modinfo -F signer nvidia`, `nvidia-smi`, and synthetic CUDA/NVENC operations under both `aura` and `curio`. When upgrading the kernel, install the matching `linux-modules-nvidia-595-server-open-<kernel>` package before rebooting; installing only userspace libraries does not provide that module. No DKMS or CUDA development toolkit is needed. The normal driver package supplies device nodes, udev rules and the persistence daemon. The application users need no additional group for the packaged NVIDIA device permissions.

Aura and Curio select `/opt/aura/bin/image-gpu/bin/python` from the same root-owned, read-only nvImageCodec/nvJPEG/CV-CUDA environment. The isolated CPython 3.14 runtime is managed by the official `uv` CLI and reconstructed from Aura's `deploy/install-image-gpu.sh` and hash-pinned `deploy/image-gpu-requirements.txt`. Each application embeds its own worker and retains independent data and concurrency limits; sharing the environment does not share catalogs, originals or a host-wide GPU semaphore. Preserve the selected runtime while either application's unit references it. A changed dependency lock requires a new runtime directory and validation under both runtime users before changing their interpreter selections. Model/runtime installations are outside the [data-protection scope](retention.md#data-protection-scope); retain reconstruction records and preserve live files independently. Aura's GPU child processes exit after 30 seconds idle so the device can suspend.

A live driver change requires the discrete GPU to have no consumers or connected display; the internal AMD display is separate. Package aliases can make `modprobe -r nouveau` act on `off` instead of unloading the loaded Nouveau module, so verify the actual module/PCI binding before proceeding. See [queued NVIDIA udev events](common-issues.md#nvidia-modules-cycle-after-replacing-nouveau-live) if modules cycle after the transition. Verify the restored package rules and actual application-user encoding before reporting activation. A host reboot remains separately authorized because all nine applications run on NAS.

### Maintenance download proxy

When a maintenance download on `nas` fails because of network reachability, the user authorizes installing an agent-friendly proxy client and importing the existing `vps` VPN node. Prefer an official command-line client such as sing-box for headless operation; Hiddify is also acceptable when appropriate. Use software-installation for installation and [VPS proxy operations](vps-proxy.md) to locate the authoritative private VLESS/REALITY settings. Import the existing node without rotating its credentials or changing the VPS listener.

Keep the local client configuration private and bind its HTTP/SOCKS listener to loopback. Apply the proxy to the affected maintenance command or package-manager invocation, preserving direct SSH, LAN, application and reverse-tunnel routes. Verify one HTTPS download through the client and resume the original failing operation. Public documentation records the setup and use, never the node URI, UUID, private key or other credentials. This is an authorized fallback; successful direct downloads do not require installing or enabling a proxy client.

Once the host has booted with `processor.max_cstate=1`, a separately authorized restart without that parameter is required to expose deeper states again. Keep the charge limit, lid policy, and network settings independent of this diagnostic rollback. The overnight boot's retained journal and sysstat data end at 02:40:05. CPU idle time in the last several ten-minute samples was approximately 99.9%, with zero I/O wait; this does not identify the precise freeze time. The subsequent failed boot's persisted journal ends during early userspace initialization, so it does not establish a password/authentication cause. Both drives again reported zero media/data-integrity errors. The machine has two matching Samsung 32 GB DDR4-3200 modules, no ECC, and BIOS G733QR.331.
