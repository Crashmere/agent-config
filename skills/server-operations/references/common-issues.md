# Common Issues and Shared Solutions

This file records issues that may affect multiple applications and their shared solutions: hosts and networking, shared Nginx, common release and backup patterns, runtime dependencies, and similar concerns. When one project encounters such an issue, document the solution here and cover every affected application. Project docs should retain only project-specific parameters and a link here rather than duplicating the procedure. Keep issues that affect only one application in that project's docs.

For each issue, document the symptoms and decision criteria, affected applications, handling steps, cleanup and acceptance checks, and improvements that have not yet been implemented. Rewrite an entry when its solution is superseded; Git preserves the history.

## Distribution-specific inspection and login notices

The `vps` image is AlmaLinux, whereas `ali` and `nas` use Ubuntu. An absent UFW executable or Ubuntu Nginx directory does not establish a host failure. The shared `inspect.sh` selects the installed firewall tool and inspects Nginx directories only when present. Verify both active firewall rules and cloud-side access separately.

Ubuntu runs `/etc/update-motd.d` scripts; AlmaLinux's SSH PAM configuration uses `pam_motd.so` and reads static `/etc/motd.d` snippets. `sync-docs.sh` maps the notice according to `SYNC_HOST=vps`; it must not introduce unconditional shell startup output, which can break command and file transfers. All applications on `ali` keep their existing notice and configuration; this difference concerns `vps` host bootstrap only.

## Host-wide stale unit-cache warnings after Snap refresh

On `nas`, `NeedDaemonReload=yes` appeared on all seven business services, Portal Web/collector, Nginx, both tunnels, SSH, chrony, and journald while those services remained healthy. A completed automatic `snapd` refresh added its mount links under `multi-user.target.wants` and `snapd.mounts.target.wants` just after systemd finished reloading. No persistent loaded fragment, drop-in, or generator source had changed afterward. The unit lookup cache was stale; the warning did not identify an unapplied Portal service change. The active `ali` and `vps` gateway services were unaffected.

Before clearing a host-wide warning, inspect concrete units' `FragmentPath`, `DropInPaths`, `SourcePath`, and `NeedDaemonReload`, compare effective settings with their current definitions, and check the unit lookup directories and relevant package-operation history. Use the last completed PID1 reload's JSON journal `__REALTIME_TIMESTAMP` when comparing modification times: ordinary second-resolution output cannot distinguish links created milliseconds after that reload from its own generated files. Runtime `/proc` and transient `/run` records are not persistent source edits. Review unexplained configuration changes before loading them.

Once the differences are accounted for and `systemctl list-jobs` shows no pending jobs, run `systemctl daemon-reload` under the shared NAS maintenance lock. This refreshes unit definitions and dependencies without restarting services. Confirm `NeedDaemonReload=no`, no failed units, and unchanged main PIDs, start timestamps, and restart counters for business services, Portal, Nginx, tunnels, and management services. Then check NAS LAN HTTPS and both gateway entrances. The NAS fix preserved all 15 checked service processes; no unit edit, service restart, or host reboot was needed.

## Interface discovery blocked by a service sandbox

On `vps`, sing-box configuration validation passed but startup failed with `initialize network: create netlink socket: address family not supported by protocol`. The unit inherited an Xray-oriented `RestrictAddressFamilies` allowlist containing only `AF_INET AF_INET6 AF_UNIX`; sing-box also uses `AF_NETLINK` to discover network interfaces. Add only that family to the affected unit, validate the unit, reload systemd, and confirm startup and a real proxy request. Do not remove the whole allowlist or grant `CAP_NET_ADMIN` for read-only interface discovery. The source is [the vps proxy unit](../assets/vps/vps-proxy.service); all applications on `ali` and `nas` remain unchanged. Apply the same diagnosis to another daemon only when its logs show this failure.

## Whole-host freezes with no retained panic

On `nas`, both the local console and network have stopped responding, including an overnight idle episode; the user also reports freezes under Windows. Retained logs contained no conclusive panic, OOM, or storage failure. Preserve journals and hardware state before further resets, check activity and SMART/self-test evidence, and investigate hardware/firmware alongside Linux drivers when the symptom crosses operating systems. An abruptly ending journal does not identify the exact freeze time or prove a thermal, memory, or driver cause.

The NAS mitigation and diagnostic sources are maintained in [freeze diagnostics](nas-host.md#freeze-diagnostics): balanced firmware profile, disabled boost, C1 idle restriction, and persistent minute health records. A later home check showed roughly 35 hours of uninterrupted idle operation and no minute-sampling gap beyond 61 seconds. This does not identify the cross-OS freeze cause or establish loaded-service reliability. The user deferred further investigation and accepts proceeding with migration under that residual risk. If freezing recurs, preserve available evidence and inspect hardware/firmware alongside drivers; do not automatically reboot or change several power settings together.

## Network startup waits for an unplugged interface

On `nas`, Wi-Fi acquired an address but `systemd-networkd-wait-online.service` timed out after two minutes, leaving the host degraded. The installer configured the unplugged Ethernet interface as required, and Netplan generated a wait-online command that waited for it as well as Wi-Fi. This host-level delay would affect every application depending on `network-online.target`.

Mark the unused Ethernet interface `optional: true` in Netplan and enable `dhcp4` so it works when a cable is connected. Keep the working Wi-Fi configuration and its credentials intact. The source for this host is `assets/nas/ethernet.yaml`; install it mode 0600 at `/etc/netplan/80-nas-ethernet.yaml`, run `netplan generate`, then `systemctl daemon-reload`, `networkctl reload`, and `networkctl reconfigure enp2s0`. Reset and start the failed wait-online unit, then verify Result=success and a new SSH connection. This procedure avoids restarting the active Wi-Fi interface.

## Restricted reverse-SSH key is unreadable

On a gateway, a correct NAS tunnel key can still be rejected if the dedicated user's root-owned `.ssh` directory is mode 0700: OpenSSH reads authorized keys as that user and cannot traverse the directory. Follow [the restricted identity ownership/modes](nas-migration.md#host-roles-and-traffic), preserving root write control and group read/traverse access. Inspect authentication logs and effective Match settings, then validate a fresh tunnel with only the permitted loopback listeners. Do not work around unreadable files by enabling a shell, widening forwarding, or changing administrator keys. This applies independently to ALI and VPS.

## Stale reverse-SSH session blocks tunnel recovery

On `vps`, public TLS and Nginx remained available while application requests timed out. The `nas` tunnel client had disconnected and was repeatedly failing with `remote port forwarding failed for listen port 18080`; the gateway's old `nas-tunnel` SSH session still held all reverse listeners, with unacknowledged TCP data and repeated retransmissions. NAS applications and the independent `ali` tunnel remained healthy. Listener existence alone did not establish a working forwarding path. That incident affected the original eight applications behind the gateway and its loopback NAS management route; the VPS proxy on TCP 443 is independent.

The same restoration failure occurred on `ali` on 2026-11-03. After heartbeat failures at 20:15:34 and 20:16:52, NAS logged 296 reverse-bind failures from 20:16:59 through 20:46:45 before a persistent session returned at 20:46:50. Successful gateway authentication did not restore forwarding while an older session retained the ports. ALI then had `ClientAliveInterval 0`, so the initiating transport failure acquired a roughly 30-minute stale-port restoration delay. The maintained server-heartbeat policy was installed on ALI and its NAS client reconnected on 2026-11-04; both gateways now run it.

After authorized diagnosis, identify the exact stale session from `ss -ltnp`, confirm its `nas-tunnel` identity and failed upstream response, and send TERM only to that session. The supervised NAS client can then reconnect without changing ports, keys, Nginx, or application data. Do not terminate the main sshd process or unrelated sessions. Use the healthy alternate gateway's existing loopback management route if the failed gateway cannot reach NAS, retaining the verified NAS host key.

The maintained gateway SSH drop-in sets `ClientAliveInterval 15` and `ClientAliveCountMax 3` only within `Match User nas-tunnel`. NAS already uses the corresponding client-side server-alive settings. The server-side probes bound retention of an unresponsive session to roughly 45 seconds rather than waiting for TCP retransmission exhaustion; they do not prevent network interruptions. Validate with `sshd -t` and effective per-user `sshd -T -C` settings, confirm administrator settings are unchanged, and reload sshd. Existing sessions retain their old settings, so reconnect the affected tunnel after the reload. Verify direct forwarded health, public login/TLS, anonymous API rejection, the alternate gateway, and unchanged proxy/runtime processes. [NAS migration](nas-migration.md#host-roles-and-traffic) records rollout scope.

## Reverse-SSH transport outages and retry storms

On `nas` and `vps`, established SSH sessions have lost heartbeat responses and fresh connections have stalled during the handshake while NAS applications and the independent `ali` route remained healthy. TCP inspection found the VPS SSH banner received but client bytes unacknowledged; VPS subsequently logged authentication timeouts and `penalty: exceeded LoginGraceTime`. The former five-second restart loop repeatedly attempted connections during those penalties. Missing VPS reverse listeners made Portal return 503 and protected business requests return 500 through a failed authentication subrequest, even though Nginx and public TLS were running. This affects all inventory applications and the VPS loopback NAS management route, not the independent proxy on TCP 443.

Curio's separate application-only tunnels carry port 18088 but still depend on Portal authentication through port 18085 in the original tunnel. A healthy Curio media forward therefore cannot keep protected public access working when the original Portal forward is unavailable. Identify the failed instance and its retained listeners before reconnecting; a Curio-only tunnel change does not repair the shared authentication path.

The 2026-11-04 comparison found nine correlated ALI/VPS heartbeat failures on 2026-11-03, within one to four seconds of each other around 16:31, 16:42, 17:09, 17:20, 17:52, 18:19, 19:18, 19:53 and 20:15 (Asia/Shanghai). NAS remained on its seven-day boot; 2,090 minute health samples across November 3 and the following morning had a maximum gap of 60.623 seconds, including the outage wave. All applications remained active, with no matching Wi-Fi carrier loss, driver reset, kernel fault or resource-exhaustion evidence. These simultaneous failures prioritize the shared NAS Wi-Fi/router/upstream path, but the logs do not identify the failing component. Current signal strength, cumulative receive drops and PCI runtime state do not establish historical Wi-Fi behavior. The alternate gateway is a separate remote route, not protection against their common NAS-side path.

VPS observed a NAS public-source change around November 3 20:17, after which one tunnel session lasted over 12 hours. On November 4, VPS-only failures detected at 08:54:15, 10:02:21 and 10:38:06 took approximately 9m36s, 2m03s and 9m35s respectively to regain gateway authentication, while ALI remained connected. These durations start at SSH failure detection, not the first lost packet. At 10:38:05 the VPS child explicitly logged a client-heartbeat timeout; NAS's subsequent `closed by remote host` was its consequence. VPS had no SSH/Nginx/proxy restart or matching resource/network failure. The earlier source's session durations also varied; the evidence does not establish a fixed nine-minute timeout or identify a carrier/provider fault. Shared-path interruptions and later VPS-specific transport failures must be investigated separately.

Compare `journalctl -u sshd` (or Ubuntu's `ssh` unit) with `journalctl _COMM=sshd-session`: PAM can move authenticated session children into another cgroup, so the service-unit filter alone can omit the decisive heartbeat messages. Correlate client and gateway timestamps, authenticated session identity, bind failures and TCP acknowledgments. Treat restart counters as retry counts, not distinct network outages, and source penalties as recovery amplification unless they precede the initial failure.

The NAS-only [VPS retry override](../assets/nas/vps-tunnel-resilience.conf) is installed at `/etc/systemd/system/reverse-tunnel@{vps,curio-vps}.service.d/10-resilience.conf`. It retains each instance's SSH command, identity, host verification, forwarding restrictions and keepalives, and sets a fixed `RestartSec=30`. Effective `RestartSteps=0` and `RestartMaxDelayUSec=infinity` are systemd defaults. This allows at most two starts per minute per instance and avoids carrying a two-minute retry delay into a later failure after a healthy session. ALI instances retain their five-second base-unit retry. Keep VPS per-source penalties enabled rather than exempting carrier networks or weakening authentication.

The retry delay limits repeated handshakes; it does not repair a broken transport. VPS's 120-second `LoginGraceTime` can retain a preauthentication connection after a shorter client timeout if teardown packets are lost, so retries may still encounter source penalties. Removing DSCP markings did not prevent a reproduced handshake timeout; the original QoS settings are retained. Successful large-packet ICMP checks did not establish that SSH traffic was passing. The provider, middlebox or host-network cause remains unidentified.

Remote observation uses [observe-tunnels.sh](../scripts/observe-tunnels.sh) on NAS and VPS. Launch one transient `systemd-run --collect` service per host with `RuntimeMaxSec=24h`, `KillMode=control-group`, a five-second stop timeout, `UMask=0077`, `Nice=10`, `MemoryMax=64M`, `CPUQuota=5%`, `TasksMax=32`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `PrivateTmp=yes`, and `ReadWritePaths=/var/log/nas-tunnel-diagnostics`. Create that parent as root-owned 0700 first. Invoke `/bin/bash /opt/server-context/scripts/observe-tunnels.sh <nas|vps> /var/log/nas-tunnel-diagnostics/<new-run> 86400 <peer-addresses>`; NAS peers are ALI then VPS from its existing tunnel configuration, while VPS uses the current authenticated NAS public source. Existing run directories are rejected. No persistent unit, timer, listener or runtime identity is added.

The root-private run contains initial interface/route metadata, approximately 15-second sleeps between samples of NAS router/gateway ICMP, tunnel state, narrow `ss -tinop` output and Portal health status/duration with bodies discarded. NAS also makes fresh HTTP/1.1 HTTPS GET requests to the public Portal login on ALI 443 and VPS 8443, discarding bodies and recording status and TCP/TLS/total durations with normal certificate validation. These independent controls distinguish SSH stalls from broader destination-path failures; they do not change the capture-trigger state. `control.txt` saves TCP SYN/FIN/RST summaries for the specified SSH peers; `bursts.txt` saves an initial baseline and short 30-second/120-packet header bursts after a health, active-retransmission or tunnel-state transition. For the isolated WireGuard comparison below, set `UDP_PEER=10.77.250.1` on NAS and `UDP_PEER=10.77.250.2` on VPS in the observer service environment. Each sample records the WireGuard endpoint, latest handshake and transfer counters, plus a 1,200-byte DF ICMP probe to the opposite peer. NAS additionally requests the synthetic `/healthz` every sample and the 16 KiB `/payload` every fourth sample, discarding response bodies and recording status, durations and byte count. UDP probe failures join `sample_state`, which is a merged TCP/UDP capture trigger rather than an outage count. `udp-control.txt` records text UDP 51821 headers on the external interface: NAS filters to its VPS peer, while VPS accepts any source on this dedicated test port so carrier NAT roaming does not silently drop candidate evidence. The SSH source filter remains independent of the WireGuard endpoint.

All captures are text summaries only, with no `-w`, `-A` or `-X` and no packet-body dumps. Sample logs are capped at 16 MiB for one SSH port, or 32 MiB when UDP is enabled or multiple SSH ports are selected. SSH control and burst logs are capped at 8 MiB each; optional UDP-control headers have a 16 MiB allowance based on the short run's observed rate. A UDP-enabled run therefore retains at most 64 MiB plus small metadata/events per host. Cap writers are unbuffered so low-rate output is immediately visible and survives the service deadline. Files are 0600; a cap may stop that stream before the 24-hour deadline. VPS `tcpdump` and dependencies were installed from official AlmaLinux repositories without updates or service restarts. Reuse NAS's existing minute health/sysstat records rather than adding GPU or storage probes.

Recover an interrupted observation with a new run directory and service, preserving old files and marking the gap; do not restart a run against its original directory. An additional UDP window requires cleanup of both lifetime owners, fresh private runtime configuration, renewed runtime firewall rules and new observer directories. Verify changing file sizes and recent complete samples on both hosts, not just active unit state.

The external capture interface and VPS SSH-source filter are fixed for a run. Route changes and a changed authenticated NAS source are recorded; restart the observer with the new interface/source selection when required. Preserve useful evidence outside Git until reviewed; stop a run with `systemctl stop <observer-unit>` and remove only identified disposable diagnostics afterward.

### Independent UDP tunnel comparison

The authorized candidate is a separate, authenticated WireGuard link between `nas` and `vps`, not a production forwarding replacement. Interface `wg-udp-test` uses VPS `10.77.250.1/32` and NAS `10.77.250.2/32`, MTU 1280, and only the opposite peer's `/32` in `AllowedIPs` and the route table. VPS listens on UDP 51821; NAS uses the VPS endpoint already available through trusted host configuration and a 15-second persistent keepalive. No NAT, IP forwarding, default route, LAN route, application route or production SSH change is part of the test. These constraints keep all NAS applications, production gateway tunnels and VPS proxy TCP 443 outside candidate traffic.

Use [wireguard-test.sh](../scripts/wireguard-test.sh) as the root-only setup/cleanup hooks. Before provisioning, check kernel/tool availability and conflicts for the interface, private subnet/peer route, nftables table, test listener and existing VPS firewalld rules. Generate fresh independent peer keys and exchange only their public halves through trusted SSH. Stage each host's private configuration under root-owned 0700 `/run/tunnel-udp-test`, with `wireguard.conf` and key material mode 0600; never commit them or copy production tunnel keys. The setup hook repeats resource checks and creates a private `owner` marker containing the host role and systemd `INVOCATION_ID` only after preflight succeeds. Setup requires a service invocation, and cleanup refuses to remove network resources unless that same invocation armed ownership of this run.

Start one transient `tunnel-probe-udp-wg.service` on each host, with `Type=exec`, `Restart=no`, `RuntimeMaxSec=24h`, `KillMode=control-group`, `TimeoutStartSec=30s` and `TimeoutStopSec=30s`; the stop allowance includes firewalld cleanup RPCs. `ExecStartPre` invokes `/bin/bash /opt/server-context/scripts/wireguard-test.sh setup <nas|vps> 86400`; the main process sleeps for the bounded window, and `ExecStopPost` invokes the corresponding `cleanup` hook. Set `RuntimeDirectory=tunnel-udp-test`, mode 0700 and `UMask=0077`, without runtime-directory preservation, so systemd removes private configuration after cleanup. The root owner uses `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `MemoryMax=64M`, `CPUQuota=50%`, `TasksMax=32` and address families `AF_INET AF_INET6 AF_UNIX AF_NETLINK`; writable paths are its runtime directory and, on VPS only, `/opt/tunnel-tools`. The setup/cleanup CPU allowance accommodates repeated firewalld CLI startup; the active owner only sleeps. Start VPS before NAS and record both deadlines privately. Do not enable a test unit at boot.

The setup hook passes the private configuration to `wg setconf` through an anonymous stdin pipe: Ubuntu's packaged AppArmor profile restricts on-disk configuration paths, so direct `/run` reads fail even as root. No profile or file-permission relaxation is needed. It reads the active VPS `drop` target from `firewall-cmd --zone=drop --list-all`; `--get-target` is permanent-only on this firewalld version. The hook adds only runtime VPS public UDP 51821 access with a 24-hour timeout. Interface-scoped `inet tunnel_udp_test` nftables guards on both hosts allow exact-peer ICMP, established replies and VPS synthetic TCP 19090, dropping other candidate input and all forwarding to or from the interface. VPS additionally assigns the interface to the existing `drop` zone with temporary exact-peer ICMP/HTTP exceptions. No permanent public-zone or production rule is edited. A firewalld reload can remove runtime allowances and interrupt the test; record that interruption rather than treating the candidate as reload-resilient.

Build [udp-probe/main.go](../scripts/udp-probe/main.go) locally as a static Linux/amd64 binary and hash-verify `/opt/tunnel-tools/udp-probe` on VPS. Run it under transient `tunnel-probe-udp-http.service` with `DynamicUser=yes`, an empty `CapabilityBoundingSet`, a five-second stop timeout, and both `After=` and `BindsTo=tunnel-probe-udp-wg.service`. It listens only on `10.77.250.1:19090` and allows requests only from `10.77.250.2`. GET/HEAD `/healthz` serves a fixed marker; `/payload` serves 16,384 deterministic bytes. Other sources, methods and paths are rejected. The server reads no files, contacts no upstream and exposes no business data. Confirm the peer probe works while public/non-WireGuard access to 19090 is denied.

Start fresh NAS/VPS observers with the UDP environment described above, their own 24-hour maximum, and both `After=` and `BindsTo=tunnel-probe-udp-wg.service` on the local host. Owner termination therefore stops observation even if an observer's own deadline is later. Acceptance first requires a handshake, both directions of 1,200-byte DF ping, the synthetic health/payload response, exact `/32` routes, private listener/firewall boundaries, and unchanged application/gateway/proxy health and production processes. This establishes setup only. Compare separately the UDP probes, WireGuard endpoint/handshake/transfer, TCP retransmissions and production forwarded-health failures over the bounded window. WireGuard handshakes are periodic, so an old timestamp alone is not an outage. If UDP stays healthy during a TCP forwarding failure, that is protocol/path-selective evidence, not proof of a carrier cause or acceptance for production traffic. Candidate NAT source changes may differ from the SSH source and must be included in that interpretation.

To stop early, stop the lifetime owner on both hosts; its dependencies stop the observers and VPS HTTP service, its hooks remove only the owned interface, peer route, nftables guards, VPS runtime rules and disposable VPS probe binary, and systemd removes the private runtime configuration. Confirm all dependents have stopped, UDP 51821 is closed, TCP 19090 is absent, and no test routes/guards/units remain enabled or active. Review private evidence before removing the identified run directories; cleanup does not target application data/derivatives, dependency caches, journals or real backups. A future production UDP switch requires a separately reviewed forwarding/access contract and authorization.

## Portal API List Does Not Match the Service

This applies to each service's `docs/API.md` and `deploy/portal.json.apis`. A successful portal receipt proves only that the declaration was loaded. The shared validator checks formatting, ownership, and resource boundaries; it does not compare declarations with business routes to verify that APIs really exist or that the list is complete. Documentation that puts multiple APIs in one table cell, extracts only the first table, or treats actions on the same path as separate APIs can leave errors and omissions even when the files synchronize successfully.

Use the current service's route registration and handlers as the authority for methods, internal paths, parameter locations, return values, and authentication notes. Inspect every route file, including endpoints registered in loops. List restricted media variants such as main and thumb separately. In the project API table, put only one method and path on each row; the path field must not contain a query string, enumeration comma, second method, or body action. Put parameters and actions in the description. Compare the portal declaration and API table item by item, add omissions, and remove nonexistent or duplicate entries. Do not extract paths from narrative prose merely by splitting on spaces.

After correcting source files, run the shared `validate-portal.py` and separately compare the entry set and semantics with the implementation; format validation does not replace that review. For documentation-only changes, first confirm that the relevant route code matches the deployed version, then run `make portal` according to the [portal release protocol](portal.md#shared-validation-and-release-protocol) and synchronize documentation with `sync-docs.sh <project-name>`. Verify the hash actually loaded by the portal and the documentation source. Do not restart a business service for a documentation correction or validate the list with production write requests.

There is currently no release gate that automatically compares each business route with its declaration. An agent changing an interface must still perform the review above. If a feature has not yet been deployed, release its declaration with the corresponding program version; do not describe a source-only API as already available in production.

## Shared Authentication Incorrectly Blocks Large Requests

Symptom: a business request returns 500 while the Nginx error log contains `client intended to send too large body`, `subrequest: "/_portal_device_check"`, and `auth request unexpected status: 413`, with no corresponding request in the application's journal. This was confirmed on 2026-10-01 when RecipeBox uploaded an approximately 4.4 MiB photo and reproduced in isolated Nginx: 1 MiB passed, while one additional byte failed.

Cause: a business location's `client_max_body_size` does not propagate to the authentication subrequest location. `/_portal_device_check` previously inherited Nginx's 1 MiB default. Even with `proxy_pass_request_body off` and an empty `Content-Length`, Nginx checks that limit against the original request length before entering the proxy phase. A 413 from the authentication subrequest is not an authentication result accepted by auth_request, so the client ultimately sees 500.

| Application | Existing ingress and program limits | Impact |
| --- | --- | --- |
| RecipeBox, FabricWorld | Nginx 26 MiB; 25 MiB per image | Normal images over 1 MiB could be blocked incorrectly |
| Yuyan | Nginx 26 MiB; 25 MiB per image; 16 MiB JSON | Large images and large document saves could be blocked incorrectly |
| Ledger | Nginx and JSON both 2 MiB | Requests of 1–2 MiB could not reach business validation |
| FeeTable | Nginx 2 MiB; JSON 64 KiB | Normal business input was unaffected; the service still inherited shared authentication |
| ServerPortal | Nginx and JSON both 1 MiB; performs its own authentication | Does not use this subrequest and was unaffected |

Keep the fix only in `location = /_portal_device_check` in shared `assets/nginx-portal-auth.conf`: set `client_max_body_size 0;` while retaining `internal`, `proxy_pass_request_body off`, the empty `Content-Length`, and cookie validation. Each business location and backend continues to enforce its own size limits. Do not disable limits at the entire http/server layer or bypass authentication for business APIs to work around the failure.

Before applying the change, use all existing locations, an isolated loopback Nginx, and synthetic authentication and business upstreams to verify normal and large requests for every site, missing and forged credentials, requests exceeding business ingress limits, authentication failures, cookie renewal, and the inability to reach the internal authentication path externally. Confirm that the bytes and hashes received by the business upstream match and that the authentication upstream receives no request body; isolated checks need not write real business data. Install to `/etc/nginx/snippets/portal-auth.conf` according to the authorization table, retain the old configuration, and gracefully reload only after `nginx -t` succeeds; restore the old configuration on failure. Then verify health for every inventory application, public icon GET/HEAD requests, unauthenticated page redirects, and API rejection. ## Top of an iPhone Home-Screen Page Appears Blurry

User report: after being added to the home screen from iPhone Chrome, Ledger, FeeTable, FabricWorld, and RecipeBox had a blurry area near the time and battery indicators, while Yuyan did not. The key code difference was positioning. Yuyan used `position: sticky; top: 0`; three older services used normal-flow headers. A [WebKit engineer's explanation of top-color extension](https://bugs.webkit.org/show_bug.cgi?id=301756#c2) says the browser extends a solid background from fixed or sticky elements at the viewport edge to avoid a gap above them during scrolling; the iPhone browser UI itself has a softer blur underneath. This provides a mechanism for the observed code difference. Desktop browser validation alone cannot prove that the home-screen appearance is fixed on a particular iPhone.

Resolution: all four services use a solid `sticky; top: 0` header. Ledger retains its internal content scrolling and header dimensions; the other three retain document scrolling, route restoration, and modal scroll locking. Applications receiving new sticky headers reserve top space for controls and anchors, and FabricWorld's desktop photo bar now sticks below navigation. All four viewports also match Yuyan and use the default safe-area layout. The user confirmed on a real device that removing only Ledger's `viewport-fit=cover` did not fix the blur, changing FeeTable to sticky fixed its top area, and then changing only Ledger from relative to `sticky; top: 0` fixed it as well. This confirms the role of explicit sticky positioning in this issue; safe-area settings alone are neither the cause nor the solution. Equivalent FabricWorld and RecipeBox changes have been released and passed browser regression checks but have not received separate real-device confirmation. No Nginx, PWA identity, database, or system-status-bar changes are needed.

Validate at two levels. Desktop Chromium/WebKit checks only the header position, scrolling, navigation, forms, and modals at 320/375 px and desktop sizes; it does not reproduce or prove removal of the native iPhone blur layer. Confirm the final result on a real iPhone by reopening the site from the home screen and scrolling in both directions. Prefer fully closing and reopening that home-screen window to load new HTML/CSS before clearing site data. The pages and Ledger manifest use no-cache, and no Service Worker is registered. Code differences alone cannot establish the native rendering cause for a particular iOS version, and they do not justify adding supposedly universal CSS to "disable system blur."

For safe-area behavior, see WebKit's official [Designing Websites for iPhone X](https://webkit.org/blog/7929/designing-websites-for-iphone-x/): `viewport-fit=cover` extends the page to the screen edges and requires developers to account for safe-area insets. <a id="systemd-沙箱下照片硬链接备份失败"></a>
## Photo Hard-Link Backups Fail in a systemd Sandbox

This applies to historical ALI native snapshots for FabricWorld, RecipeBox, Yuyan, and any explicitly authorized operation that hard-links data files into its backup directory. SQLite-only snapshots are unaffected. FabricWorld and RecipeBox were fixed and verified by the following method on 2026-09-24; Yuyan used this configuration at installation on 2026-09-26 and was verified through its unit. NAS full external backups cold-copy files instead and do not use this timer/hard-link workflow.

Symptom: `<app>-backup.service` fails every time, with `hard-link media backup: link ... invalid cross-device link` in the journal. The initial backup made manually with runuser during installation does not use the unit sandbox and therefore does not expose the issue. The two applications consequently failed for five days from their first scheduled runs before discovery.

Cause: the unit used `ProtectSystem=strict` and `ReadWritePaths=/opt/<app>/data /opt/<app>/backups`, causing systemd to bind-mount the two directories as separate mount points. Linux cannot create hard links across mount points, even when the underlying filesystem is the same, and returns EXDEV.

Fix: use `ReadWritePaths=/opt/<app>` in the backup unit, placing data and backups under one writable mount point. Everything else under `/opt/<app>` is owned by root, and file permissions already prevent the application user from writing there, so the effective write scope does not change. Update `deploy/<app>-backup.service` in the project repository and push it, install it to `/opt/<app>/config/`, then run `systemctl daemon-reload`; the resident service unit does not need a change. Failed runs leave no incomplete backup directory, so there is nothing to clean up.

When verifying an authorized legacy native-snapshot run, `systemctl show <app>-backup.service -p Result` must report success, its `daily-*` directory must contain `manifest.json`, and the photo hard-link count (`stat -c %h`) must be greater than 1. Verify the real unit sandbox, not only a manual runuser command. Do not enable a NAS backup timer for this check; [manual full backups](nas-migration.md#manual-full-backups) define the NAS operation.

Real backup deletion or restoration still follows the shared authorization table.

## Native media processing exhausts a service task limit

On `nas`, Aura bulk imports exhausted its former `TasksMax=128` budget. The limit counts threads in the entire service cgroup, including Go, codecs, FFmpeg and private Python workers. Symptoms included `Resource temporarily unavailable`, failed `fork`/`pthread_create`, stuck decoder children and Go `fatal error: newosproc`, followed by systemd restarts. An `active` unit or a successful health request between restarts does not establish processing health.

Compare `systemctl show aura -p TasksCurrent -p TasksMax -p LimitNPROC -p NRestarts` with `/sys/fs/cgroup/system.slice/aura.service/pids.{current,max,events}` and `ps -e -o pid,ppid,nlwp,comm --sort=-nlwp`. A rising cgroup `max` event counter identifies task-budget rejections independently of free RAM. `VIPS_CONCURRENCY=2` does not cap all codec-owned threads; individual HEIC subprocesses reached 15–28 threads. Do not raise user-wide limits when the service cgroup is the actual constraint.

Aura's source unit now uses a 1024-task budget, with eight jobs, at most four ExifTool/libvips/CPU video operations and four GPU operations. Upload capture-date extraction shares the CPU bound. Native helper pools have explicit thread settings, and command/request deadlines cancel stalled children and release slots. Install the maintained project unit under the shared maintenance and application deployment locks, reload systemd, and restart only Aura. Validate HEIC/RAW and mixed-media queues under the real runtime identity/cgroup, including interruption recovery and cgroup task events, then retry failed resources through the application's bounded API. Preserve accepted originals. Curio uses two jobs and one GPU slot in its separate 1024-task unit; these are application-level limits, not a host-global semaphore. Future applications using native codec pools should measure their complete process trees rather than copying Aura's task count.

## FFmpeg recompiles CUDA kernels for every short job

On `nas`, FFmpeg's `scale_cuda` repeatedly JIT-compiles CUDA kernels when its runtime user cannot write the driver cache. Aura and Curio have root-owned, read-only service homes at `/opt/aura` and `/opt/curio`, so the default `~/.nv/ComputeCache` is unavailable. CUDA/NVENC can still succeed while this startup cost dominates short segment generation.

Check the runtime user's `HOME`, `CUDA_CACHE_PATH`, `CUDA_CACHE_DISABLE`, cache ownership and systemd write restrictions. Repeat one identical synthetic `lavfi` CUDA-scaling/NVENC command under that identity and sandbox, using the same private writable cache for both runs; compare elapsed time and cache-file growth. An isolated NAS one-frame check under `aura` took about 6.9 seconds cold and 0.4 seconds warm, with about 5.1 MiB of cached kernels. Administrator-run GPU success alone does not check the service's cache access.

Keep the sandbox and select a bounded, application-owned runtime cache. The maintained NAS units set `CUDA_CACHE_PATH=/run/aura/playback` with `RuntimeDirectory=aura`, and `/run/curio/playback` with `RuntimeDirectory=curio`; both set `CUDA_CACHE_MAXSIZE=33554432`. Each cache is independently owned disposable tmpfs state outside originals, installed models and recovery material. Systemd removes it when the corresponding service stops, so the first use after restart can compile again. Install the maintained unit and reload systemd under the shared maintenance/deployment locks, restarting only the affected application; verify the warm-cache result afterward.

## NVIDIA modules cycle after replacing Nouveau live

On NAS, a live switch from Nouveau to Ubuntu's NVIDIA server driver can leave queued udev `remove` events interleaved with new `add` events. The packaged `71-nvidia.rules` runs `modprobe -r` for dependent modules on driver removal; stale events can unload the newly loaded base driver, causing another add/remove cycle. Symptoms include repeated `nvidia-drm` loading/unloading, persistence daemon restarts, intermittent `nvidia-smi` failures, and CUDA initialization errors. Inspect the kernel journal and udev worker commands before treating this as a GPU hardware failure.

For a confirmed installation-time cycle with no GPU consumers, temporarily copy `/usr/lib/udev/rules.d/71-nvidia.rules` to the same basename under `/run/udev/rules.d/`, omitting only the `ACTION=="remove", DEVPATH=="/bus/pci/drivers/nvidia"` lines. Reload udev rules and drain events with a bounded `udevadm settle`, load `nvidia` and `nvidia_uvm`, then drain events again. Remove the temporary override and reload the original rules after the device is stable. Verify CUDA/NVENC under the actual application identity and confirm that kernel events stop cycling. Leave package-owned rules unchanged. This procedure affects NVIDIA consumers on NAS, currently Aura and Curio; the internal display remains on AMD. Future driver transitions should prefer a separately authorized reboot when live unload prerequisites are not met.

## HTTP/2 Flow Control Slows Streaming Uploads

On NAS with Nginx 1.28.3, Aura's HTTP/2 uploads with `proxy_request_buffering off` transferred a 128 MiB chunk in about 49 seconds, while the server returned confirmation roughly 50 milliseconds after the request body finished. The delay occurred during transmission. Increasing the application chunk size did not enlarge Nginx's HTTP/2 receive window.

Nginx defaults `http2_body_preread_size` to 64 KiB. Small stream receive windows can force repeated waits for window updates on a LAN with measurable latency. An isolated NAS Nginx instance, a synthetic sink that discarded uploaded bytes, and the same 128 MiB payload through one trusted SSH connection measured 14.9 MB/s with HTTP/1.1, 3.5 MB/s with default HTTP/2, and 14.9 MB/s with HTTP/2 plus `http2_body_preread_size 4m`. These are decimal MB/s measured through the test tunnel, not a promise of production or physical-link throughput. A separate 128 MiB write on the NAS application filesystem took about 33 milliseconds plus 58 milliseconds for fsync.

Further isolated comparisons with 1, 4, 8 and 16 MiB windows measured 9.7, 13.4, 11.0 and 11.9 MB/s respectively; larger windows did not produce a sustained gain. A final comparison with the uploader paused measured 9.78 MB/s for HTTP/2 with 4 MiB, 9.37 MB/s with 16 MiB, and 10.00 MB/s for HTTP/1.1 through the same SSH transport. Production Aura chunks improved from about 49 seconds to 12–13 seconds per 128 MiB with 4 MiB, and 8 MiB produced similar 12–13 second chunks. Wi-Fi variation affects comparisons, so choose the smallest window that removes the repeatable protocol bottleneck rather than treating the largest value as fastest.

The shared NAS, VPS and ALI HTTPS templates use `http2_body_preread_size 4m`. This per-request buffer applies to all applications sharing the server; their upload limits, streaming policy, authentication and durable acknowledgment remain application-owned. [Upload throughput and request limits](conventions.md#upload-throughput-and-request-limits) maps those contracts and owns the maintenance procedure. The directive belongs to `http` or `server` scope. Follow the [authorization table](../SKILL.md#authorization) before activation, preserve the existing host-rendered configuration, validate Nginx and reload gracefully, then check each application and unauthenticated access. See the [Nginx HTTP/2 module reference](https://nginx.org/en/docs/http/ngx_http_v2_module.html#http2_body_preread_size).
