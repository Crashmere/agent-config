# 技术方案与叙述汇报编写

先根据用户指明或读者对象选定写作模式，读取对应参考，再按下面的共通规则写作与修订。

## 一、先确定写作模式

- **技术方案模式**：用户明确说写“技术方案”，或内容面向研发设计、方案评审、技术回复、代码解释、注释与维护文档时采用。动笔前先读 [技术方案模式编写指南](references/tech-design.md)。
- **叙述汇报模式**：用户明确说写“叙述汇报”，或内容面向项目概览、复盘、案例分析、收益分析、立项或阶段答辩时采用。动笔前先读 [叙述汇报模式编写指南](references/narrative-report.md)。
- **混合场景**：同一文档兼顾两类读者时，按章节明确区分深浅——汇报部分不堆代码细节，落地设计部分不空谈概念。

## 二、设计前置与详略原则

1. **先查复用，再做新设计**：动笔设计前，先看现有组件、接口、流程或数据模型能不能直接支持；如果两套东西干的是同一件事，优先合并或抽公共逻辑，并写清参考了哪份现有实现、改了哪里。
2. **权衡抽象成本，写明取舍**：复用和通用性不是越高越好，要算清楚实现、理解和维护成本；只有明确存在共性需求时才做抽象，范围别画太大。把真正影响选型的权衡直接写出来。
3. **按模式定深浅**：
   - **技术方案**：先把结论和改动主线放在开头，再顺着因果和数据流展开实现细节；影响业务语义、跨端契约、动态配置、错误处理和边界条件的地方写透，常规解析与样板逻辑一句话带过。
   - **叙述汇报**：站在管理层和跨团队读者的角度写，开头先亮出全貌、重点和核心结果，再按「背景与痛点 → 怎么判断问题 → 整体方案与破局点 → 实际收益」往下展开，靠具体机制和前后数据说话，代码细节外链出去。

## 三、两类场景共通规范

### 1. 说人话、去“文档腔”
写文档时，保持**和同组同事在对话框里把事讲明白**的直白程度，只删掉“大家好、其实、就是说”这类纯口语词，**不要为了显得“正式”把话写绕**：

- **多用具体动词，少用抽象大词**：能写“拆开、合并、跳过、改配置、少调一次、先算再写”，就不要写成“实现……收敛 / 完成……赋能 / 构建……范式 / 形成……闭环 / 沉淀底座”。
- **拆开长定语，一句话只讲一件事**：一旦写出“基于……通过……实现了……的……”这种多层嵌套长句，立刻拆成两三句短句。
- **别硬凑四字加粗前缀**：列表项能直接说事就直接说，不要为了排比给每条硬套抽象的四字小标题。
- **两步法保住直白语气**：如果用户是先在对话里聊清方案、再让你整理成文档，只做标题、表格和画板整理，**保留原话的直白用词，不要二次“润色”成书面黑话**。
- **术语前后统一**：全文对同一个概念只用一个固定叫法。

正反改写对照（成稿前对照自查一遍）：

| 别这么写（文档腔） | 这么写（直白清楚） |
| --- | --- |
| 通过将识别与处置阶段解耦，实现单次合并落库，消除多模块并发覆写与回擦隐患 | 先把所有模块算完，选出唯一结果，最后只写一次库，去掉原来的边算边写和擦掉重写 |
| 完成多场景底座沉淀与口径拉齐，赋能下游零侵入平滑切换 | 审核、特征生产、样本打包共用同一套拉数逻辑，下游 11 个模型不用改代码 |
| 依托动态配置化能力，显著提升业务策略迭代的敏捷性与交付效率 | 调策略不用改代码发版，改完 TCC 配置 5～15 分钟生效 |
| 针对外部大模型调用高延迟与不稳定性，构建异步解耦与容错兜底机制 | 大模型慢且偶发失败，改成发 MQ 异步调、结果再回调，失败不卡主链路 |

### 2. 结构、表格与画板
- **每件事只在一个地方讲透**：开头概览可以点明关键决策，细节放到后面对应章节讲，需要时简短回指。删掉反复强调“非常重要”的废话、只把本节重复一遍的结尾总结，以及只用来预告下一节的过渡句。
- **多维度内容优先用表格替代列表**：推理用连贯段落，简单一维并列用列表；只要信息带多个维度或重复字段（尤其是容易写成多层嵌套无序列表的内容），改用**表格**，更紧凑也更好扫读。不硬套固定模板，也不把连贯逻辑拆成一堆细碎小节。
- **善用画板和文档特殊模块**：灵活使用当前文档工具的**画板、高亮块、表格、分栏**（飞书文档配合 `lark-doc` / `lark-whiteboard`；个人知识库 Yuyan 配合 `yuyan-doc` 及 `references/drawing.md`）。讲流转逻辑、状态变化、前后对比或模块顺序时，优先用画板代替大段文字。
- **画板用图形说话、少堆字**：画板内容同样服从对应模式的要求（汇报画板保持高层视角、突出对比和收益）。靠**形状、箭头、分区、实虚线和颜色对比**直接表达意思，框里只写精简短词，不在图上堆长段说明或大块气泡——让读者一眼看懂，而不是点开图再读一堆字。画板风格按模式区分，见对应指南与示例图。

### 3. 事实边界与证据
- **分清现状、拟议和未知**：把现有行为、计划改成的行为、还没定下来的未知项明确分开。事实要对得上代码、配置、接口或可靠资料；性能数据、兼容承诺和验证结论必须有证据；没定下来的事直接点出具体哪里未决。改写已有内容时，保住原事实、数字、主体、适用范围和确定程度，不把不确定的事写成确定，也不把相关写成因果。
- **用机制和结果说明价值**：别空泛夸“更稳定、更灵活、性能好”，直接说清楚组件在什么时候做了什么、带来什么具体好处或代价。
- **代码注释**：只写非显而易见的设计意图、约束或兜底原因，不复述代码字面意思。

### 4. 防冗余与文档修订
- **有话直说，去掉多余防御句**：直接说实际行为、条件和后果。看到像在“防杠”的句子，问一句：谁会看它？删掉后会不会产生实质误导？没有明确歧义的人为对比、表功式铺垫、提前道歉、多余的排除声明一律删掉；堆叠的模糊限定词合并成一个；真正会改变语义的限制紧跟在结论旁边，编者自查笔记放工作记录，别塞进脚注。
- **不写改动清单、修订时重写成当前版本**：所有文档都不附带“改动清单 / 变更记录 / 修改文件汇总 / 本次更新说明”这类内容——变更历史留给 Git 或文档版本记录，文档只呈现当前完整的设计、现状与约束。修订文档时把受影响的段落重写顺畅，删掉作废结论、废弃分支和“此前讨论过……”“本文略去……”这类依赖对话上下文的话；保留给新读者看的简明选型理由，只在专门留档历史决策的记录里保留历史分支。
- **完稿通读复核**：交稿前通读一遍全文（含图注、开头和交付说明），做一次**去文档腔、去冗余防御句**检查；如果原文已经直接准确、没有实质改进空间，就不必为了改而改。
